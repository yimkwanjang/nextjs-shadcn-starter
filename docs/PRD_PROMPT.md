당신은 B2B SaaS 제품의 시니어 프로덕트 매니저이자 기술 PM이다.
지금부터 **"노션에 입력한 견적서를 클라이언트가 웹에서 확인하고 PDF로 내려받는 서비스"**
의 **MVP PRD(제품 요구사항 정의서)** 를 작성한다. 응답과 산출 문서는 모두 한국어로 쓴다.

## 0. 작성 전 필수 절차 (건너뛰지 말 것)

1. **모호한 전제는 추측하지 말고 먼저 질문한다.** 아래 항목 중 내가 명시하지 않은 것이
   PRD의 범위를 실제로 바꾸는 경우에만, **최대 4개까지** 골라 한 번에 물어본 뒤 답을 받고
   작성을 시작한다. 범위를 바꾸지 않는 항목은 합리적 기본값을 정하고 "가정" 절에 기록한다.
   - 견적서를 만드는 사람: [[예: 나 혼자 / 영업팀 3명 / 외부 파트너 포함]]
   - 월 발행 건수와 클라이언트 수: [[예: 월 20건, 고객사 10곳]]
   - 클라이언트 인증 방식: 공개 링크(추측 불가 URL) vs 비밀번호 vs 로그인 계정
   - 노션 데이터 구조: 견적서 1건 = 데이터베이스 1행인가, 페이지 1개인가,
     품목 목록은 어디에 있는가(하위 테이블/관계형 DB/페이지 본문)
   - 견적서에 담기는 필수 항목: [[예: 공급자/공급받는자 정보, 품목·수량·단가, 공급가액,
     부가세, 합계, 유효기간, 비고, 도장/서명 이미지]]
   - PDF 디자인 요구 수준: 사내 표준 양식 재현 필수 vs 깔끔하면 충분
   - 다국어·다통화 필요 여부, 세금계산서 연동 필요 여부
   - MVP 목표 시점: [[예: 3주 내 첫 고객 전달]]

2. **기술 전제를 코드베이스에서 확인한다.** 작성을 시작하기 전에 반드시
   `/Users/brightmacbookpro/workspace/courses/invoice-web/CLAUDE.md` 와 같은 위치의
   `AGENTS.md` 를 **Read로 열어** 실제 스택과 함정을 파악한다. PRD의 기술 섹션은
   **그 문서에 기록된 스택을 전제로** 쓴다. 학습 데이터의 관례로 추측하지 않는다.
   특히 다음은 CLAUDE.md에 명시된 이 저장소의 확정 사항이므로 위반하지 않는다.
   - Next.js 16 (App Router, Turbopack) · React 19.2
   - TailwindCSS v4 — `tailwind.config` 파일이 **없다**. 테마 토큰은 `src/app/globals.css` 의 `@theme`
   - shadcn/ui는 Radix가 아니라 **Base UI** — `asChild`가 없고 `render` prop을 쓴다
   - 경로 alias `@/*` → `src/*`
   - `my-app/` 디렉터리는 프로젝트 본체가 아니므로 참조하지 않는다
   - 라우트 그룹 `(app)` / `(auth)` 구조와 `nav-config.ts` 불변식(링크 추가 시 페이지도 추가)
   Next.js API를 언급해야 한다면 `node_modules/next/dist/docs/` 의 해당 가이드를 먼저 확인한다.

3. **노션 연동은 사실 확인이 필요한 영역이다.** Notion API의 인증 방식, 데이터베이스 조회
   방법, 요금/레이트리밋 등 최신 확인이 필요한 내용은 추측해서 단정하지 말고
   ① 공식 문서를 확인하거나 ② 확인이 불가하면 "검증 필요" 표시를 달아 남긴다.

## 1. 제품 개요 (이 문제의 본질)

현재 [[나/우리 팀]]은 견적서를 노션에 정리해 두고, 고객에게는 매번 수기로 문서를 만들어
보내고 있다. 이 반복 작업을 없애는 것이 목표다. 즉 **노션이 단일 진실 원본(SSOT)이고,
웹은 읽기 전용 표현 계층, PDF는 그 표현의 고정 산출물**이다. PRD 전반에서 이 원칙을 유지하라.

## 2. PRD 필수 목차

아래 순서와 제목을 그대로 사용한다. 각 절은 **판단 근거가 드러나게** 쓴다.

1. **문서 정보** — 작성일, 버전, 작성자, 상태(Draft/Confirmed)
2. **배경과 문제 정의** — 현재 워크플로의 구체적 병목, 이를 방치할 때의 비용
3. **목표와 비목표(Non-goals)** — MVP에서 **하지 않을 것**을 명시적으로 나열.
   비목표가 없는 PRD는 반려 대상으로 간주하고 반드시 채운다.
4. **성공 지표** — 정성 목표가 아니라 측정 가능한 수치로.
   (예: 견적서 1건 발행 소요시간 20분 → 2분, 링크 열람률, PDF 다운로드 성공률)
5. **사용자와 시나리오**
   - 페르소나 2인: **발행자**(노션에 입력하는 사람), **클라이언트**(링크를 받는 사람)
   - 각 페르소나의 End-to-End 시나리오를 서술형으로 1개씩
6. **핵심 사용자 흐름** — Mermaid 다이어그램으로 표현하고, 아래를 반드시 포함
   - 노션 입력 → 발행(링크 생성) → 클라이언트 열람 → PDF 다운로드
   - 견적서 내용 수정 시 이미 배포된 링크가 어떻게 동작하는가(재검증/캐시 무효화)
7. **기능 요구사항** — 표 형식. 컬럼: `ID | 기능 | 사용자 스토리 | 수용 기준(Given-When-Then) | 우선순위`
   - 우선순위는 **MoSCoW**(Must/Should/Could/Won't)로 표기하고,
     **Must는 MVP를 정의하는 최소 집합으로 엄격히 제한**한다.
   - 최소한 다음 영역을 다룬다:
     노션 데이터 동기화 · 견적서 목록/상세 · 공개 링크 발행과 접근 제어 ·
     견적서 웹 뷰(반응형) · PDF 생성 및 다운로드 · 만료/폐기 처리 · 오류 상태 처리
8. **데이터 모델** — 노션 속성 ↔ 앱 내부 타입의 **매핑 표**를 만든다.
   컬럼: `노션 속성명 | 노션 타입 | 앱 필드명 | 앱 타입 | 필수 | 비어 있을 때의 동작`
   TypeScript 인터페이스 정의도 함께 제시한다.
9. **화면 정의** — 화면별로 목적/주요 구성요소/상태(로딩·빈 상태·오류·만료)를 기술.
   최소: 견적서 목록(내부용), 견적서 공개 상세 뷰, 잘못된·만료된 링크 페이지.
   레이아웃은 ASCII 와이어프레임으로 스케치한다.
10. **기술 설계 개요**
    - 아키텍처 다이어그램(Mermaid): 노션 API ↔ 서버 ↔ 브라우저
    - **PDF 생성 방식은 선택지를 비교한 뒤 하나를 추천**한다.
      최소 3안(브라우저 인쇄 CSS / 서버 헤드리스 브라우저 / 클라이언트 JS 라이브러리)을
      `방식 | 한글 폰트 | 레이아웃 충실도 | 인프라 비용 | 구현 난이도 | 결론` 표로 비교하고,
      **한글 폰트 깨짐과 페이지 나눔(page-break)** 문제를 반드시 평가 항목에 넣는다.
    - 데이터 페칭·캐싱 전략, 노션 API 레이트리밋 대응
    - 시크릿(노션 토큰) 취급 방식 — 절대 클라이언트로 노출하지 않는 설계임을 명시
11. **보안·프라이버시** — 견적서는 금액이 담긴 민감 문서다.
    링크 추측 가능성, 검색엔진 색인 차단, 접근 로그, 만료 정책을 다룬다.
12. **범위 밖(Out of Scope)과 향후 로드맵** — MVP 이후 2~3단계
13. **가정과 열린 질문** — 확정되지 않은 전제를 전부 나열. 각 항목에 **결정 필요 시점**을 붙인다.
14. **리스크와 대응** — `리스크 | 영향 | 발생 가능성 | 완화책` 표
15. **마일스톤** — 주 단위. 각 주의 **검증 가능한 산출물**을 명시

## 3. 작성 원칙

- **MVP 규율**: "있으면 좋은 것"을 Must에 넣지 않는다. 어떤 기능을 Must로 판단했다면
  그 근거(없으면 제품이 성립하지 않는 이유)를 한 줄로 남긴다.
- **구현이 아니라 요구를 쓴다.** 다만 기술 선택이 제품 경험을 좌우하는 지점
  (PDF 생성 방식, 링크 접근 제어)은 예외로 깊게 다룬다.
- **모든 기능 요구사항에는 수용 기준이 있어야 한다.** 테스트로 옮길 수 없는 문장은 쓰지 않는다.
- **불확실한 것은 불확실하다고 쓴다.** 확인하지 않은 API 동작이나 요금을 단정하지 않는다.
- 표·다이어그램을 적극 사용하고, 장황한 서술을 피한다.
- 영어는 코드 식별자와 고유명사(Notion, Next.js, PDF 등)에만 쓴다.

## 5. 제출 전 자기 검증

작성을 마치면 아래를 스스로 점검하고, 통과하지 못한 항목은 고친 뒤 제출한다.

- [ ] 비목표 절이 비어 있지 않은가
- [ ] Must 기능만으로 "노션 입력 → 클라이언트가 PDF를 받는다"가 끝까지 완주되는가
- [ ] Must 중 빼도 그 완주가 되는 항목이 있는가 (있다면 Should로 강등)
- [ ] 모든 기능 요구사항에 Given-When-Then 수용 기준이 있는가
- [ ] 노션 속성 ↔ 앱 필드 매핑에서 **빈 값·누락 시 동작**이 정의되었는가
- [ ] 한글 PDF 폰트 문제를 명시적으로 다뤘는가
- [ ] 노션 토큰이 브라우저로 새지 않는 구조임이 문서상 분명한가
- [ ] 추측으로 단정한 외부 API 동작이 남아 있지 않은가
